### V2-141 — Static application production behavior (all 8 sub-bullets)

This was the biggest surprise of the pass: V2-141 turns out to already be
fully implemented and tested, because the static-serving infrastructure
(`firmware/components/web_server`, `scripts/build-webfs-image.sh`,
`scripts/verify-no-remote-assets.sh`) was built well before Phase 14 was
reached — it just had never been checked off. Verified with real commands:

```bash
npm --prefix webapp run build
# dist/assets/index-DNGRoJPY.css, dist/assets/index-Dyil3X-o.js  (content-hashed)
./scripts/verify-no-remote-assets.sh webapp/dist   # exit 0
./scripts/build-webfs-image.sh --skip-frontend-build
# webfs image written: firmware/build/webfs.bin (1048576 bytes, partition budget 1048576 bytes)
./scripts/run-tests.sh web   # 23/23 passed, includes test_blob_load_rejects_path_traversal
```

Webfs margin computed the way `scripts/check-release-budgets.sh`'s
`littlefs_used_bytes()` does (count non-erased 4096-byte blocks, since the
raw LittleFS image file is always padded to full partition size):
**393,216 bytes used / 1,048,576 bytes partition = 37.5%**, well inside the
85% budget ratio (891,289 bytes). The full `check-release-budgets.sh` script
itself needs a completed `idf.py -C firmware build`, which this pass did not
run (not needed to reproduce its webfs-specific number by hand).

Content-type mapping, gzip-variant selection, and cache-control (`no-cache`
for `index.html`, `public, max-age=31536000, immutable` for hashed assets)
are all exercised by `test_static_file_selection()` in
`tests/host/test_web_server_adapter_json_static.inc`. "Never expose the
userdata mount" is structural, not just tested: the only catch-all route in
`firmware/components/web_server/web_server_lifecycle.c` is
`{.uri = "/*", .handler = static_handler}` fixed to the `/web` base path;
userdata/blob access exists only through the separate `/api/v1/blob*` JSON
routes.
