### V2-091 — "Show Add macro, Edit, Send, and overflow controls."

This was the specific line the task asked to verify precisely. Investigation:

- **Add macro**: a direct header button in `MacrosPage.tsx` (`webapp/src/features/macros/v2/MacrosPage.tsx`), tested in `tests/v2-macros-page.test.tsx::"shows ordered macros, macro count, and Add macro"`.
- **Send**: a direct per-row button, extensively tested across the V2-093 `describe` block.
- **Edit**: a direct per-row button with an `aria-label` naming the macro, `onClick` calling `onOpenEditMacro(macro.id)`. Traced the full production wiring by reading code (not assuming): `AppV2.tsx` passes an `onOpenEditMacro` handler that calls `navigateToEditMacro(macroId)`; `webapp/src/v2/routingV2.ts`'s `navigateToEditMacro` encodes the macro ID into the hash; on the next route, `macroEditorTargetFromHash()` parses it back into an edit target carrying that same ID; `AppV2.tsx` passes that ID as `MacroEditorPage`'s `macroId` prop; `MacroEditorPage.tsx` calls `findMacro(repository, macroId)` and seeds its name/source/timing state from the located macro. Each link in that chain has its own direct test (`v2-routing.test.ts`'s hash-parsing and `navigateToEditMacro` tests; `v2-macro-editor-page.test.tsx`'s tests that construct `MacroEditorPage` with a `macroId` and assert the right fields load; `v2-app-v2.test.tsx`'s Add-macro round-trip integration test for the create path through real routing). What was **missing** before this audit: no test clicked the Edit button itself and asserted it invokes `onOpenEditMacro` with the clicked row's macro ID — the callback existed and was wired correctly by inspection, but nothing proved the button-to-callback link at the unit level. Per the task's explicit allowance, added exactly one test to close this: `webapp/tests/v2-macros-page.test.tsx::"MacrosPage — V2-091 macro list > Edit calls onOpenEditMacro with exactly the clicked row's macro ID"` (clicks the Edit control for one row, asserts `onOpenEditMacro` was called exactly once with that row's macro ID, not the other row's). No other file touched for this.
- **Overflow controls**: a `MacroOverflowMenu` (Preview and send/Duplicate/Delete with name-bearing confirmation), added in Phase 10's V2-101, tested in `tests/v2-macros-page.test.tsx::"MacrosPage — V2-101 overflow menu (Duplicate/Delete)"` (3 tests) and `"the overflow menu still offers Preview and send"`. UI_UX_SPEC_V2 §5.1 lists "Preview and send, Duplicate, Move, and Delete" as overflow examples ("such as"); Move is implemented as direct Move up/down buttons rather than inside the overflow menu, which satisfies §5.1's separate "reorder affordances" bullet and does not contradict the "such as" phrasing.

All four sub-requirements are present in production code and now have direct test coverage. Checked, with the reasoning and citations above recorded inline in `docs/TODO_V2.md`.

**Command run:** `npm --prefix webapp run test` (after adding the one test) -> `523/523 passed` (51 files). `npx vitest run tests/v2-macros-page.test.tsx --reporter=verbose` confirms the new test runs and passes: `MacrosPage — V2-091 macro list > Edit calls onOpenEditMacro with exactly the clicked row's macro ID`, 31ms. `npm --prefix webapp run typecheck` and `npm --prefix webapp run lint` both clean after the addition.
