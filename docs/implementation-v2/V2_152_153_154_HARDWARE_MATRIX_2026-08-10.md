## 1. A second real, previously-undiscovered production bug — found and fixed

While testing V2-153's reprovisioning flow, found that **first-run setup
never restarted the device**, despite its response claiming
`restartRequired: true` and `connectionWillClose: true`. Reproduced live:
submitted valid setup credentials, got `202 accepted`, but the device never
left setup mode (`GET /api/v1/setup` kept reporting `provisioned:false`;
login stayed disabled since it's only enabled in normal mode). Confirmed the
settings genuinely *had* committed — resubmitting the same setup code
afterward correctly got `409 already provisioned` — so this wasn't a data
problem, just a missing restart.

**Root cause:** `setup_submit_handler()` (`web_server_setup.c`) is its own
dedicated `httpd_uri_t` registration (`web_server_lifecycle.c`'s
`setup_routes[]`), bypassing the generic `api_handler()` dispatch entirely —
the same pattern login/logout use. That generic dispatch is the *only* place
`esp_restart()` was ever called, gated to `/api/v1/device/restart` and
`/api/v1/device/factory-reset` only. Setup submission had no code path to
ever reach it. `webapp/src/features/auth/v2/FirstRunSetupPage.tsx` already
tells the user *"The device applied your configuration and is restarting its
Wi-Fi"* — confirming an automatic restart was always the intended behavior,
not a manual step.

**Fix:** call `esp_restart()` after a successful response send, mirroring
`web_server_api.c`'s `api_handler()` exactly (commit `0c51b76`).
`tests/host/test_web_server_setup_route.c` previously covered only `GET
/api/v1/setup` by explicit design, with `setup_submit_handler()`'s
dependencies stubbed to `TEST_CHECK(false)` — exactly why no host test could
have caught this. Added real fakes and two regression tests (successful
submission restarts exactly once; a rejected one never restarts). Verified:
56/56 host tests, `--sanitizers` clean, `check-firmware.sh` clean (GCC +
esp-clang clang-tidy, zero first-party findings).

**Verified fixed on real hardware**, capturing the boot log through a full
factory-reset → setup cycle:

```text
[setup POST returns 202]
...
rst:0xc (RTC_SW_CPU_RST),boot:0x8 (SPI_FAST_FLASH_BOOT)
...
I (1020) app_core: stage complete: nvs
...
I (1230) app_core: stage complete: usb        <- normal-mode-only stage
I (1230) app_core: stage complete: executor    <- normal-mode-only stage
I (1240) app_core: stage complete: controls    <- normal-mode-only stage
```

No `"device is unprovisioned"` warning this time — the device restarted
automatically and came up directly in normal mode. Confirmed via HTTP:
`GET /api/v1/setup` → `404`; login with the new credentials → `200`.

  `executor_confirmation_tests.inc`, `executor_execution_tests.inc`). On
  real hardware, the compiler's `APP_V2_ESTIMATED_DURATION_MAX_MS` (300s)
  caps any acceptable macro to within 10 seconds of the 310s absolute
  deadline — that gap is a safety margin for anomalies (USB stalls, retries),
  not something a valid macro can be constructed to reliably cross without
  an unbounded, unreliable wait or artificial fault injection. Left open
  rather than claimed or faked.

## 4. V2-154 — Network and authentication matrix

- **First-run setup:** covered by §1/§3 above (now includes the restart fix).
- **Unauthenticated setup-state GET, minimal response, 404 after
  provisioning:** confirmed throughout §1/§3 (`GET /api/v1/setup` behaves
  correctly both while unprovisioned and after).
- **Login:** real successful logins throughout this session and prior ones.
- **Logout:** `POST /api/v1/auth/logout` → `204`; the same session cookie
  immediately gets `401` afterward on a real subsequent request — genuinely
  invalidated server-side, not just cleared client-side.
- **Lockout — full real lifecycle:** 5 real failed logins → `401` each; 6th
  → `429` with `Retry-After: 300`; a **correct** password during the window
  also correctly got `429` (not a bypass); waited out the real 300-second
  window (polled every 10s) and confirmed login succeeded again once it
  cleared.
- **Idle expiry (24h) / absolute expiry (7d):** not independently verified
  on hardware this session — these are real multi-hour/multi-day wall-clock
  waits, not something to fake by shortening production timers. Covered
  deterministically by host tests (`tests/host/auth_existing_tests.inc`).
  Left open rather than claimed.
- **AP availability after station failure:** attempted `wifi-connect` with a
  deliberately wrong password. Real firmware behavior: three bounded
  connection attempts (~9 seconds total, not an unbounded retry loop), a
  clean `connection failed: internal` error, and `wifi-status` afterward
  confirmed `AP state: ready` — completely unaffected by the station
  failure, matching `SPEC_V2` §12.1's requirement exactly.
- **Bounded reconnect behavior:** demonstrated immediately after the above —
  a subsequent `wifi-connect` with correct credentials succeeded cleanly, no
  lingering bad state from the prior failure.
- **Password change and PBKDF2 timing:** PBKDF2 timing already covered in
  `docs/implementation-v2/V2_041_HARDWARE_LOGIN_FIX_2026-08-09.md`. Password
  change tested fresh: `POST /api/v1/settings/change-password` → `204`; the
  session cookie active at the time of the change was immediately
  invalidated (`401` on the next request) — matching `SPEC_V2` §13.9's "a
  successful password change invalidates all sessions including the current
  one"; the old password then correctly failed login (`401`); the new
  password correctly succeeded (`200`).
- **No secret in logs/HTTP/diagnostics/exports:** spot-checked (not a full
  audit — that remains the open, partial item already tracked at the Phase 4
  exit gate) by grepping every serial/HTTP log captured this session for the
  live admin password string; no match. Consistent with, not a replacement
  for, the existing automated `check-credential-logging.sh` source scan and
  secret-sentinel test coverage.

## 6. Commands run

```bash
. "$HOME/esp/esp-idf-v5.5.5/export.sh"
nvm use 24.18.0
cd firmware && idf.py build
bash ../scripts/generate-flash-manifest.sh   # gitCommit 0c51b76
idf.py -p /dev/ttyACM1 flash                 # native USB, bootloader mode

# factory reset + reprovisioning (station mode throughout except the
# unavoidable brief setup-AP connection needed to reach the device before
# it has any station credentials):
curl -X POST http://<station-ip>/api/v1/device/factory-reset \
  -d '{"adminPassword":"...","confirmation":"FACTORY RESET"}'
# (boot log captured over the UART console during the restart)
curl -X POST http://192.168.4.1/api/v1/setup -d '{"setupCode":"...", ...}'

# lockout lifecycle:
for i in 1..6: curl -X POST .../auth/login -d '{"adminPassword":"wrong-N"}'
# poll every 10s until a valid login succeeds again (real 300s wait)

# password change:
curl -X POST .../settings/change-password \
  -d '{"currentPassword":"...","newPassword":"..."}'

# station-failure / bounded-reconnect (serial console, /dev/ttyACM0):
wifi-connect "Revival Hall" "definitely-wrong-password"
wifi-status
wifi-connect "Revival Hall" ""
```
