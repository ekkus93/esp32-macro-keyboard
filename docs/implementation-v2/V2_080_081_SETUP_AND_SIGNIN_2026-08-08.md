## Audit finding: the existing auth scaffolding speaks the wrong API

Before writing any code, `webapp/src/features/auth/LoginPage.tsx`, `SetupPage.tsx`, and
`SessionBoundary.tsx` were read in full, per this task's instructions. All three are v1
scaffolding, not v2-adaptable in place:

- `SetupPage.tsx` calls `GET /api/v1/setup-state` and `POST /api/v1/setup/credentials`
  — routes that do not exist in `docs/SPEC_V2.md` §13.3's route table (v2 has exactly
  `GET`/`POST /api/v1/setup`, no `-state` or `/credentials` suffix, and no
  `/api/v1/setup/restart` — v2's setup POST response itself carries
  `connectionWillClose`, there is no separate restart call).
- `LoginPage.tsx` posts `{"password": ...}` (v1 field name) against the v1
  `{ok,data}`/`{ok,error}` envelope via `api/client.ts`'s `apiRequest`, not v2's flat
  `{authenticated,...}` / `{error:{code,message,...}}` shape.
- `SessionBoundary.tsx` composes both of the above plus a v1 `DeviceStatus` type
  (`version`/`idf`/`wifiState`/...) that has no relationship to v2's
  `StatusResponse`.
- All three are still exercised by the existing `webapp/tests/app-auth.test.tsx` against
  `App.tsx`'s current, fully v1-shaped `AuthenticatedApp` (package/macro CRUD,
  `activePackageId`, plural `/api/v1/executions`-era flows) — which is itself explicitly
  **not** this task's scope to rewrite (that's Phase 9-11 territory per
  `docs/implementation-v2/V2_MIGRATION_MAP.md` §3.5-3.7).

Given that, editing those three files in place would either leave them speaking the wrong
API (if only partially touched) or cascade into rewriting `App.tsx` and its whole existing
v1 test suite — both outside this task's explicit scope boundary ("don't try to wire the
entire startup decision tree yourself"). This mirrors the precedent Phase 7 already set
(`docs/implementation-v2/PHASE_7_REPOSITORY_CORE_AND_PERSISTENCE_CLIENT_2026-08-08.md`):
new v2-correct code was added alongside the untouched v1 code, without wiring it into
`App.tsx`, with the wiring explicitly left to a later phase.

**Decision:** build V2-080 and V2-081 as new, self-contained, exported components under
`webapp/src/features/auth/v2/`, built entirely on the already-frozen v2 contract layer, and
leave the v1 `LoginPage.tsx`/`SetupPage.tsx`/`SessionBoundary.tsx`/`App.tsx` and their
existing tests completely untouched. `routing.ts`'s `Screen`/hash-routing type was **not**
extended: it is used only for the authenticated-app's in-app navigation (`macros`,
`packages`, ...), and the existing v1 `SessionBoundary` already establishes the pattern
that pre-authentication states (setup, login) are a separate state machine rendered
outside that hash-routed `Screen` type entirely — the two new components follow the same
pattern and take a plain completion callback prop instead.

### Why the storage-prohibition scan needed widening

CLAUDE.md's task instructions call out
`webapp/tests/v2-browser-storage-prohibition.test.ts` as "the two-part static-scan-plus-
runtime-check pattern used" to follow. Reading it showed its static-scan glob was scoped
to `../src/v2/**/*.{ts,tsx}` only — it would **not** have caught a storage violation in
the new `src/features/auth/v2/` files, which is exactly where a setup code, Wi-Fi
passphrase, and administrator password live in React state. The file's own "Scope note"
already flagged this exact situation ("this satisfies V2-072 for all Phase 7 code... out
of Phase 7's scope... Flagging this for whoever picks up that phase"). This change is that
follow-through: the glob now covers both directories, and a second runtime test drives
both new pages through a complete happy-path flow (including secret-field input) before
asserting no storage write occurred. The `.test.ts` → `.test.tsx` rename was required
because the new runtime test needs to render JSX.

## Requirements traced to implementation

### V2-080 — First-run setup screens

- **Load first-run state from unprovisioned-only `GET /api/v1/setup`.** Done on mount;
  uses the existing `isSetupStateResponse` guard.
- **Reject any setup-state response with fields beyond `provisioned` and `deviceName`.**
  `isSetupStateResponse` already enforces `hasExactKeys(["deviceName","provisioned"])`
  (pre-existing Phase 1 code, unmodified); `v2GetJson` throws `V2ApiError` for a
  guard failure, and the component renders a "Setup unavailable" state rather than
  proceeding. Covered by
  `"rejects a setup-state response with fields beyond provisioned and deviceName"`.
- **Device identification and setup-code entry.** The form shows the device's current
  name (from the GET) and an 8-digit setup-code field.
- **Device name, AP credentials, administrator password, optional physical-confirmation
  fields.** All present; the "Review setup" submit button is gated by `isSetupRequest`
  (the existing Phase 1 request guard — the single source of truth for the exact byte
  bounds, so no bound is duplicated/re-invented in the component). Covered by
  `"keeps setup review disabled until every field is valid"`.
- **Review without displaying secret values.** The review step's `<dl>` shows only device
  name, AP SSID, and the physical-confirmation choice — never the passphrase, admin
  password, or setup code. Covered by
  `"review step never displays the passphrase, admin password, or setup code"`, which
  asserts the literal secret strings are absent from `document.body.textContent`.
- **Apply, restart, reconnect guidance, and Sign In transition.** `POST /api/v1/setup` on
  Apply; success shows reconnect guidance naming the new AP SSID and a "Continue to Sign
  In" button that calls `onSetupComplete`. No separate restart-endpoint call is made —
  SPEC_V2 §13.4 has no such route; `connectionWillClose: true` in the `202` response is
  the signal that the device is already restarting.
- **Keep repository creation outside provisioning.** Trivially true: this component never
  references any blob/repository endpoint.

### V2-081 — Sign In

- **Show Sign In only for a configured device without a valid session.** Implemented as a
  self-contained behavior rather than left entirely to a future composing parent: on
  mount, `SignInPage` calls `GET /api/v1/auth/session`; if a session is already valid it
  calls `onAuthenticated` immediately and the password form is never rendered. Covered by
  `"calls onAuthenticated immediately without showing the form when a session already
  exists"`. (The broader "is this even a configured device" decision remains V2-082's
  job, as scoped.)
- **Display rate-limit and lockout errors without leaking account state.** The component
  relays exactly `error.code: error.message` from the device's own response for every
  failure status (400/403/413/415/422/429/500) — it never adds its own guess about *why*
  a login failed. Covered by two tests asserting the 403 and 429 cases render the
  server's message verbatim and nothing more.
- **Redirect successful authentication into repository startup.** `onAuthenticated(session)`
  is called with the parsed `SessionStatus`; what "repository startup" means is explicitly
  the composing caller's job (V2-082), not this component's.
- **Do not add per-phone onboarding.** No onboarding/welcome content of any kind was added.

## What is not covered by this change

- **No wiring into `App.tsx`, `routing.ts`, or `SessionBoundary.tsx`.** Composing these
  two components into the full startup decision tree (unconfigured → First-Run Setup →
  Sign In → authenticated startup) is explicitly V2-082's job, which itself needs
  `GET /api/v1/settings` from a concurrent sibling stream that had not landed at the time
  of this task, per this task's own scope boundary.
- **The v1 `LoginPage.tsx`/`SetupPage.tsx`/`SessionBoundary.tsx` and `app-auth.test.tsx`
  are untouched.** They remain wired into the current v1 `App.tsx` and continue to pass
  their existing tests unmodified. Whoever does the `App.tsx`/Phase 9-11 rewrite will need
  to either delete these three v1 files and their test in favor of the new v2 components
  plus a v2 startup state machine, or otherwise reconcile them — this was flagged rather
  than silently decided, since deleting working v1-wired code was outside this task's
  scope.
- **No physical-device or live-firmware validation.** Everything was validated against
  the frozen v2 contract layer and `fakeFetch`, per CLAUDE.md's rule against claiming
  hardware validation from anything short of an actual device.
- **No Retry-After-header-driven countdown UI for 429 responses.** `docs/SPEC_V2.md` §13
  defines no `Retry-After` header or any structured rate-limit metadata beyond the generic
  error envelope, so none was invented; the server's `message` text is shown as-is.
