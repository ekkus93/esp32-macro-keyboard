### V2-111 — Snapshot management (6/6 `[x]`, all confirmed true)

Blob ID, stored size, loaded indicator, storage usage (used/remaining bytes),
and retention target all render in `SnapshotsPage.tsx:604-611` and per-row in
`SnapshotRow` (lines 178-192). Load/Download/Delete/Save current snapshot
buttons all present. No device-generated date is rendered anywhere in the
component (grep for date-formatting confirms none; also asserted by
`v2-snapshots-page.test.tsx:171` "shows no device-generated dates anywhere").
Loading is permitted at any time (no gating beyond the dirty-check, which
routes to the warning rather than blocking). Deletion requires typing the
exact blob ID (`SnapshotRow`'s `disabled={typedId !== id || anyBusy}`,

(`onDelete` → `deleteRow`), confirmed by
`v2-snapshots-page.test.tsx:729` "mounting and viewing the page never issues
a delete call on its own".

### V2-112 — Advisory retention target (5/5 `[x]`, all confirmed true)

`evaluateSnapshotRetention` (`snapshotRetention.ts`) is a pure function taking
`(count, target)`; `target` comes from `settings.snapshotRetentionTarget`
(`AppV2.tsx` passes `retentionTarget={settings.snapshotRetentionTarget}`,
sourced from the device via `getSettings()` — never hardcoded). Default `5`
is a device-side default (SPEC_V2 §11.1/§11.4), not asserted client-side,
which is correct per spec. The non-blocking indicator
(`retention.overTarget`) renders as a `role="status"` paragraph, not a
blocking dialog. Nothing in `SnapshotsPage.tsx` selects snapshots for
deletion automatically — the user clicks each row's own Delete. A sixth (or
later) save is permitted: `saveWorkingCopyAsSnapshot` never checks count
against target. Tested explicitly in
`v2-snapshots-page.test.tsx:265` "saving a sixth snapshot never triggers a
delete call, at any count above target" and in
`v2-snapshot-retention.test.ts` (4 tests: at/below target, over target,
target `0` disables, the boundary case).

### V2-113 — Dirty-work protection during load (5/5 `[x]`, all confirmed true)

`requestLoad` checks `store.getIsDirty()` and routes to a `pendingLoad` state
that renders `UnsavedChangesPrompt` with all four SPEC'd choices — verified
in the component (`SnapshotsPage.tsx:693-715`) and in the real-Chrome
scenario (`run-browser-tests.mjs:1156-1166`, which asserts the presence of
exactly `Cancel`, `Export working copy`, `Save snapshot`, and `Discard
changes and load` as buttons). `loadSnapshotIntoWorkingCopy` validates before
ever calling `store.replaceWorkingCopy` (`snapshotClient.ts:148-154`).
Stored snapshots are left untouched by loading (no DELETE/POST call in the
load path at all — confirmed by reading `loadSnapshotIntoWorkingCopy`, which
only does a GET). Package resolution after load
(`afterWorkingCopyReplaced` → `resolveSelectedPackage`, UI_UX_SPEC_V2 §3.6)
runs after every successful load.

### V2-114 — Unreadable snapshot recovery (4/4 `[x]`, all confirmed true)

`SnapshotRow` renders `loadErrorMessage` inline (`role="alert"`, exact
decompression/schema error text via `loadFailureMessage`), and the failing
row stays in the list with Download/Delete/Advanced still enabled — nothing
in `performLoad`'s failure branch removes the blob from `list` or attempts
another blob. No silent fallback: on any of the three failure reasons
(`gzip_unsupported`, `unreadable`, `invalid`), `loadSnapshotIntoWorkingCopy`
returns without ever calling `store.replaceWorkingCopy`. Tested in

### V2-115 — Import and export (6/6 `[x]`, all confirmed true)

Export produces `.emk-repository.json.gz` (`exportRepository`,
`snapshotClient.ts:221-230`); confirmed end-to-end in the real-browser
scenario, which downloads the actual file, gunzips it in Node, and asserts
the JSON matches the live working copy. Import decompresses, decodes,
parses, and fully validates before any store mutation
(`importRepository`, never touches a store). Package/macro counts are shown
before confirmation (`SnapshotsPage.tsx:749-756`, and asserted by the
browser scenario waiting for `'1 packages'`/`'1 macros'` text). Imported
data is marked dirty only via `store.applyImport` inside `applyImport`
(called only from the confirm button or the dirty-import "Discard and
import" path) — never auto-uploads (no `saveWorkingCopyAsSnapshot` call
anywhere in the import path). Exclusion of credentials/sessions/keys/
diagnostics is genuinely structural, not just asserted: I read
`repository.ts` directly and confirmed `hasExactKeys` is enforced at *all
three* levels of the schema — `repositoryKeys = ["format", "packages",
"schemaVersion"]`, `packageKeys = ["id", "macros", "name"]`, `macroKeys =
["id", "interKeyMs", "keyPressMs", "name", "source"]` — so an imported file
with any extra top-level, package-level, or macro-level field is rejected by
`invalid_fields`, not silently dropped or passed through.

*Minor wording note, no functional issue:* the checklist evidence text says
"only `format`/`schemaVersion`/`packages`/`macros` fields exist to
serialize" — `macros` is actually a package-level field, not a top-level
Repository field (the top-level fields are `format`/`schemaVersion`/
`packages`). The underlying claim (no credential/session/key/diagnostic
field exists anywhere in the schema) is still true; this is a harmless
compression of "all field names across the whole schema tree" into one list,
not an invented requirement. Left as-is — not worth a documentation churn
for a non-substantive wording nit.
