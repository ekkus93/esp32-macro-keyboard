## Checkboxes changed

Exactly **one** edit, text-only, no checkbox state change:

- **V2-050**, "Test malformed paths and unsupported methods" (line ~516,
  stayed `[ ]`). The old parenthetical — "no `esp_http_server` fake exists
  anywhere in this codebase" — was true when V2-050 was last edited but is
  now false: the V2-053 (blob) and V2-057 (route-matrix/administration)
  tracks added exactly such a fake
  (`tests/host/fakes/esp_http_server_stub/esp_http_server.h`,
  `fakes/fake_httpd.c`), now used by five test files. Reworded to state this
  accurately while explaining why the underlying gap is still real: the fake
  is a hand-built double that answers handler calls directly (`blob_list_handler(&request)`
  etc.), not ESP-IDF's actual httpd URI-trie/method dispatch, so no test —
  old or new — proves what a genuinely malformed path or wrong method
  receives from the real server before any first-party handler runs. Verified
  by reading `tests/host/fakes/esp_http_server_stub/esp_http_server.h` (no
  routing table, just struct fields and function prototypes) and confirming
  no test file calls `api_handler()`/a fixed-URI handler with an unmapped
  path or disallowed method and asserts on a live-routing-produced 404/405
  (the one 404/409 case in `test_web_server_administration_route.c` is
  `setup_route_response()`'s own provisioned-mode business-logic branch, not
  httpd routing). This was the only line in the entire Phase 5/6 range where
  the checked-in text made a verifiably false factual claim.

## Most significant findings

1. **The one text correction above (V2-050)** — a previously-true "no
   `esp_http_server` fake exists" claim went stale once later tracks (V2-053,
   V2-057) built one for other purposes, and nobody revisited this earlier
   line's wording. The underlying gap (no live-httpd-routing-level test) is
   still real; only the reasoning given was outdated. Low severity, docs-only.

2. **Real, disclosed, unresolved functional gap (not a checkbox defect):**
   `POST /api/v1/send` (`firmware/components/web_server/web_send.c`, lines
   199-207) never sets `.require_confirmation` on the
   `macro_execution_request_t` it submits — it is always left at its
   zero-initialized `false`. This means the device setting
   `requireSerialConfirmation` (SPEC_V2 §7.12: "When physical confirmation is
   enabled, an accepted send enters `awaiting_confirmation`...") has **no
   effect on real sends** even though the executor-side mechanism
   (`EXECUTION_AWAITING_CONFIRMATION`, `macro_executor_confirm()`, the
   60-second timeout) is fully implemented and host-tested (V2-061). This was
   independently confirmed by reading `web_send.c` directly (no
   `require_confirmation` or `requireSerialConfirmation` reference anywhere
   in that file or `web_server_send.c`). It does not make any individual
   V2-054 or V2-061 checkbox false as literally worded (none of those bullets
   claim the HTTP layer performs this wiring), and it is already disclosed in
   TODO_V2.md's own V2-061 evidence paragraph ("`POST /api/v1/send` does not
   yet gate on physical confirmation ... a documented, deliberate gap") — so
   no checkbox was changed for it. Flagging it here because it is a genuine,
   still-open SPEC_V2 §7.12 compliance gap spanning the Phase 5/Phase 6
   boundary, not because any checkbox misrepresents it.

3. **No fabricated or newly-discovered hardware evidence.** V2-063's
   real-device latency item, all of V2-064, and the Phase 6 exit gate's
   hardware-evidence bullet remain correctly unchecked; no attempt was made
   to claim hardware validation from this audit's host-only verification.
