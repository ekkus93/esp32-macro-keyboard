# Stack-usage allowlist for scripts/check-stack-usage.sh
#
# Format:  <max_bytes> <path>:<function>
# Lines starting with # are comments.
#
# This file is a RATCHET, not an amnesty:
#
#   * an unlisted function over the gate's threshold fails the build;
#   * a listed function that GROWS beyond its recorded number fails the build;
#   * a listed function that no longer exists fails the build (no rot);
#   * shrinking a frame means lowering its number (or deleting the line) in the
#     same change.
#
# WHY THIS GATE EXISTS
#
# Host tests run on x86, where a thread stack is megabytes, so a multi-kilobyte
# local is legal and neither AddressSanitizer nor Valgrind has anything to
# report. On the ESP32-S3 the same function runs on a FreeRTOS task stack of a
# few KiB (main_task 8 KiB, httpd 24 KiB). Before this gate existed the only way
# to find these was to crash real hardware, one endpoint at a time.
#
# CURRENT STATUS
#
# Every remaining frame fits the 24 KiB httpd task stack (largest is
# restore_locked at ~20 KB), so no HTTP endpoint is a guaranteed crash any more.
# The previously known-broken frames are fixed:
#
#   storage_repository_tree_validate  388288 -> ~1.6 KB   (exceeded total heap)
#   handle_progress_action             45424 ->    688
#   snapshot_load_locked               42336 ->      0    (inlined)
#   handle_progress_resource           29984 ->      0    (inlined)
#   validate_progress                  15056 ->    128    (boot path)
#   validate_index                      7456 ->     48    (boot path)
#
# The two validators mattered disproportionately: they run from
# storage_atomic_recover_all() during startup, on main_task's 8 KiB stack, so an
# interrupted progress or index write would have left the device unbootable.
#
# REMAINING RISK
#
# The entries below fit the httpd stack but several exceed main_task's 8 KiB.
# That is only a problem for functions reachable from startup recovery; the
# known boot-path entry points are all small now, and the one that remains
# listed (storage_transaction_recover_all_with_ops, ~5.6 KB) fits 8 KiB but
# without much margin. The dominant cause throughout is the same: fixed-size
# arrays as locals (procedure_progress_t's two app_uuid_t[200] arrays,
# storage_uuid_order_t, storage_set_index_t). The fix is always to heap-allocate
# with a single free on a single exit path.
#
# CURRENT STATUS (updated after the 2026-08-01 reduction pass)
#
# 13 frames remain over the threshold, down from 31. Every one fits the 24 KiB
# httpd task stack; the largest is restore_locked at ~20 KB.
#
# Two changes did most of the work:
#
#   * STORAGE_ORDER_MAX_IDS was APP_STEPS_PER_PROCEDURE_MAX (200) although an
#     order list only ever holds macro, procedure, or set identifiers - at most
#     APP_MACROS_PER_SET_MAX (100). Right-sizing it halved storage_uuid_order_t
#     from ~8 KB to ~4 KB and removed nine frames outright.
#   * The three storage_repository_progress.c functions now keep their ~16 KB
#     procedure_progress_t buffers on the heap.
#
# What is left is dominated by procedure_progress_t (~16 KB: two
# app_uuid_t[APP_STEPS_PER_PROCEDURE_MAX] arrays, which is a genuine bound, not
# over-provisioning) appearing inside the package import/export/replace/restore
# paths. Those need the same treatment: one allocation, one free, one exit.
#
# A caution for whoever does that, learned the hard way here: callers are
# allowed to alias a progress buffer into the output snapshot
# (test_storage_progress.c passes &snapshot.progress alongside &snapshot), so a
# copy taken before the output is cleared is load-bearing. Removing one looks
# safe and is not.
#
# Baseline measured 2026-08-01 during first hardware bring-up.
#
