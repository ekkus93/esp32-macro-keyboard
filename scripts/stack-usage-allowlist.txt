# Stack-usage allowlist for scripts/check-stack-usage.sh
#
# Format:  <max_bytes> <path>:<function>
# Lines starting with # are comments.
#
# This file is a RATCHET, not an amnesty:
#
#   * an unlisted function over the gate's threshold fails the build;
#   * a listed function that GROWS beyond its recorded number fails the build;
#   * a listed function that no longer exists fails the build (no rot);
#   * shrinking a frame means lowering its number (or deleting the line) in the
#     same change.
#
# WHY THIS GATE EXISTS
#
# Host tests run on x86, where a thread stack is megabytes, so a multi-kilobyte
# local is legal and neither AddressSanitizer nor Valgrind has anything to
# report. On the ESP32-S3 the same function runs on a FreeRTOS task stack of a
# few KiB (main_task 8 KiB, httpd 24 KiB). Before this gate existed the only way
# to find these was to crash real hardware, one crash at a time.
#
# KNOWN-BROKEN ENTRIES (exceed the 24 KiB httpd task stack; these crash today)
#
#   handle_progress_action   ~45 KB  procedure-progress complete/skip endpoints
#   handle_progress_resource ~30 KB  procedure-progress read/replace/reset
#   snapshot_load_locked     ~42 KB  full-backup export path
#
# Each holds several multi-kilobyte structs at once
# (storage_progress_snapshot_t, procedure_t, procedure_progress_t). The fix is
# to heap-allocate them, as storage_macro_list_t and storage_procedure_list_t
# already do, and as storage_repository_tree_validate now does (that one was
# ~388 KB - larger than the entire free heap - and is now ~1.6 KB).
#
# The remaining sub-24 KB entries are latent rather than actively crashing: they
# fit the httpd stack today but leave little margin, and would overflow the
# 8 KiB main_task if ever reached from startup.
#
# Baseline measured 2026-08-01 during first hardware bring-up.
#
